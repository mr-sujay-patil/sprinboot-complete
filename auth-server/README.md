# Auth Server Microservice — Identity & Security Masterclass

`auth-server` acts as the Identity Provider (IdP) for the system. It handles user registration, password hashing (BCrypt), credentials validation, and issues cryptographically signed JSON Web Tokens (JWT).

---

## 1. Core Concepts Demonstrated

### A. Stateless Authentication via JWT
Traditional monolithic applications store session state on the server (e.g. `HttpSession`). In a microservices architecture, this is anti-pattern because:
- Sibling services would need a shared session store (like Redis) or sticky sessions.
- **JWT Fix:** The authentication state is stored entirely client-side inside a signed JSON token. The client sends this token in the `Authorization: Bearer <TOKEN>` header on every request.

### B. BCrypt Hashing
*   Passwords are never stored in plain text.
*   `auth-server` uses the **BCrypt Strong Hashing Function**, which incorporates a secure random salt per password to prevent rainbow table attacks.

### C. Symmetric Signing (HMAC-SHA256)
*   **Signature:** The JWT is signed using a secret string (`jwt.secret`). The signature guarantees that the header and payload have not been tampered with since creation.
*   **Security Constraint:** Any microservice validating these tokens must share the exact same symmetric key (`JWT_SECRET`).

---

## 2. Technical Framework Breakdown

### Security Architecture Classes
*   **`SecurityConfig.java`**: Configures the Spring Security filter chain. Disables CSRF (since JWT makes the application stateless and immune to CSRF), sets session management to stateless, and configures route-level authorization.
*   **`JwtUtil.java`**: Implements token construction, signature generation (HMAC), claim extraction, and expiration checking.
*   **`CustomUserDetailsService.java`**: Loads username, password, and roles from the database using Spring Data JPA.

## 3. Study Guide: JWT Token Design
Decode the token generated by this service on [jwt.io](https://jwt.io) to analyze its components:

*   **Header:** Specifies the signing algorithm (e.g. `HS384`).
*   **Payload:** Contains claims such as:
    - `sub`: Username (e.g. `dockeruser`).
    - `roles`: Authority/Role strings (e.g. `ROLE_USER`).
    - `iat`: Issued-at timestamp.
    - `exp`: Expiration timestamp.
*   **Signature:** Formed by combining the encoded header, encoded payload, and the secret key.
